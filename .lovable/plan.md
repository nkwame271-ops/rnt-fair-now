# Rent Card Revocation and Reupload

## Current state (verified)

- `rent_card_serial_stock` has a hard rule `UNIQUE (serial_number, pair_index)`, so a serial can only ever exist once per card side — revoked or not.
- Because of that rule, the batch upload screen **deletes** matching revoked rows before uploading (`SerialBatchUpload.tsx`), which destroys the revocation history.
- Serial generation in the admin action treats *any* existing row (including revoked) as a duplicate and skips it, so revoked serials can never be re-issued.
- Stock currently holds 248,361 revoked, 28,087 available and 13,956 assigned rows.
- The table records `revoked_at`, `revoked_by`, `revoke_reason` but nothing about who added or re-added a serial.

## Goal

A serial may appear many times historically, but only one non-revoked instance at a time. Revoked history is never deleted.

## Changes

### 1. Uniqueness rule
Replace the blanket unique rule with one that only applies to non-revoked rows: a serial + card side can be re-added freely once every earlier instance is revoked, but a second active/assigned instance is rejected by the database.

### 2. Reupload audit fields
Add to the stock table:
- who added the row and when
- office/region already stored, kept per instance
- a reason/note for the re-upload
- a counter or flag marking the row as a re-upload of a previously revoked serial

Existing rows keep their current values; new rows get filled in on upload and generation.

### 3. Batch upload screen
- Stop deleting revoked rows.
- Block a serial only when a non-revoked row already exists for that serial and card side; report those as skipped.
- Require a short reason when any of the incoming serials were previously revoked, and show a confirmation summary ("12 of 50 are re-uploads of revoked serials").
- Record uploader, timestamp, target office/region and reason on each new row.

### 4. Serial generation (admin action)
- Duplicate detection considers only non-revoked rows, so revoked ranges can be regenerated.
- New rows carry the same audit fields (generated by, timestamp, region, reason = batch label).

### 5. Serial lookup / history
- Serial Lookup shows every historical instance of a serial in order, each with its status, office, added-by/date, revoked-by/date and reasons, so an officer can see the full life of a serial.

## Technical notes

- Migration: drop `rent_card_serial_stock_serial_pair_unique`; create partial unique index on `(serial_number, pair_index) WHERE status <> 'revoked'`; add `created_by uuid`, `source_note text`, `is_reupload boolean default false` (plus index on `serial_number` for history reads).
- `SerialBatchUpload.tsx`: remove the revoked-delete loop; existence check filtered with `.neq("status","revoked")`; insert audit fields; keep the `generation_batches` record.
- `supabase/functions/admin-action/index.ts` (`generate_serials_multi`): add `.neq("status","revoked")` to the duplicate lookup, keep the `seenSerials` guard and the conflict-tolerant upsert (now conflict target = the partial index, so use plain insert with per-batch error tolerance).
- `SerialLookup.tsx`: query all rows for the serial ordered by `created_at`, render as a timeline.
